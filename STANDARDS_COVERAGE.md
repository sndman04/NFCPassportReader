# Ordinary-passport standards coverage

This inventory describes the published `notary-2.3.1-privacy.6-rc.7` candidate. It is an implementation and synthetic acceptance inventory, not a certification of all passports. The verified remote revision is `8b0f1ea1af90e6e331929524f40ae213125c9373`; the app may now pin rc.7 for integration/device testing. The user explicitly selected a separate project for Terminal Authentication and LDS2.

| In-scope mechanism | Acceptance evidence and boundaries |
| --- | --- |
| LDS Security Object v0/v1 | Complete version-dependent validation; original independently signed v0/v1 bytes retained. v0 excludes LDSVersionInfo; v1 requires two correctly encoded version strings. CMS SignedData is separately v3. Both verifier orders, hash comparison, `.notaryStrict`, trust, malformed/truncated/unsupported structures and post-failure scrubbing are covered. |
| Passive signature verification | RSA PKCS#1, RSA-PSS, DSA and ECDSA; SHA-1 legacy and SHA-224/256/384/512 profiles. 143 independently constructed signed profiles include 100 PSS hash/MGF/salt combinations, defaults, restricted PSS public keys, explicit EC certificate parameters, SKI and issuer/serial identifiers, certificate reordering and multiple signers. Every signature must pass; trusted verification requires every SID-matched signer's chain. Unknown algorithms and malformed declarations fail closed. |
| DG2 facial images | Legacy ISO/IEC 19794-5 plus the ICAO ISO/IEC 39794-5 application profile: JPEG and JPEG 2000, multiple BITs, version/extensions, bounds and truncation. 25 independently encoded profiles (7 accepted, 18 rejected), with signed v1 SODs and production read/result/policy checks. Image fixtures are solid color rectangles. Optional ancillary metadata is structurally bounded and discarded; this is an image reader, not an extractor/validator of every optional biometric measurement. |
| BAC / secure messaging | Existing independent ICAO command/response vectors, response-integrity mutations, replay and lifecycle tests retained. |
| PACE v2 | Independently enumerated 19 OIDs, 141 permitted algorithm × standard-parameter conversations, plus 38 explicit-parameter conversations. GM/IM DH and ECDH, ECDH-CAM, 3DES/AES variants and all 14 standard parameter sets. Table 12 excludes P-224 with IM. Explicit chip parameters must equal a known standard group; arbitrary unfamiliar groups are intentionally rejected before password-bearing exchanges. ICAO requires a standard-parameter alternative. |
| Active Authentication v1 | 44 independent RSA recovery/ECDSA profiles: RSA normal/complement recovery, all supported hash trailers, malformed headers/trailers/digests, explicit ECDSA algorithm metadata, missing/unknown/weak algorithms and oversized hashes. ECDSA requires prime curves and uncompressed points; missing DG14 does not silently imply SHA-256. Scrubbing and policy rejection are covered. |
| Chip Authentication v1 | All 8 OIDs across 14 compatible standard DH/EC parameter sets (56 conversations), plus corrupt new-session confirmation for every OID. Explicit key ID zero is preserved. Multiple cipher suites for one key are accepted, preferring AES then larger symmetric keys. Conflicting key families/versions/identifiers fail. New keys must authenticate a protected command response before success. |
| Offline document-signer revocation | Optional local PEM CRL bundle or one DER CRL, authenticated with each signer's direct issuer key. AKI binding permits issuer DN changes; issuer CRL-signing key usage is required. Highest CRL number, validity interval, revoked serials, unsupported critical/delta/indirect structures, malformed bundles and CSCA link chains are tested. No network lookup or certificate identifiers leave the process. The app maintains trusted roots and current CRLs. |

Generated PACE/CA peers share low-level library primitives. Fixed independent ICAO vectors complement those conversations. Neither replaces external conformance testing or physical NFC evidence. Bounds (including 16 CMS signers, 2 MiB CMS certificate matching, 10 MiB images and 16 MiB/1,024-CRL bundles) are deliberate resource limits, not claims of unlimited standards support.

## Standards basis

- [ICAO Doc 9303 Part 10](https://www.icao.int/sites/default/files/publications/DocSeries/9303_p10_cons_en.pdf), §§4.6.2.1–4.6.2.3, Table 37 and Appendix D: LDS/CMS versions, signed structure, signer identifiers and digest parameters; §4.5.6 for DG2.
- [ICAO ISO/IEC 39794-5 eMRTD application profile, August 2023](https://www.icao.int/sites/default/files/TRIP/Publications/ICAO-TR-39794-5-eMRTD-Application-Profile.pdf), §§2–5 and Annex A: face structure, image formats and forward-compatible extensions. Schema attribution/license is in [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md).
- [ICAO Doc 9303 Part 11](https://www.icao.int/sites/default/files/publications/DocSeries/9303_p11_cons_en.pdf), consolidated Amendment 2 dated 23 February 2026: §§6.1.2 and 9.2.4 (AA); §§6.2.3–6.2.4 and 9.2.5–9.2.7 (CA); §§9.2.1–9.2.3 and 9.5/Table 12 (PACE); §7.1 (TA), §7.2 (issuer-specific encrypted biometrics), §8.3 (revocation). CA v1, PACE v2 and AA v1 are distinct protocol versions; the SOD correction does not loosen these gates.
- [ICAO Doc 9303 Part 12](https://www.icao.int/sites/default/files/publications/DocSeries/9303_p12_cons_en.pdf), §§4.1.6.1–4.1.6.4, 6.1.2 and Appendix D.3: RSA/DSA/ECDSA/hash profiles, certificate validation and CRL key identification across issuer-name changes.
- [RFC 5652 §§5.3–5.6](https://www.rfc-editor.org/rfc/rfc5652.html#section-5.3), [RFC 4055 §3](https://www.rfc-editor.org/rfc/rfc4055.html#section-3) and [RFC 4056 §§2.2–3](https://www.rfc-editor.org/rfc/rfc4056.html#section-2.2): CMS binding and PSS parameters/key restrictions. Different content/signature hash functions are not forbidden by RFC 4056's SHOULD; the independent variation exercises actual CMS-to-manual fallback.

## Remaining work after the second audit

1. **Physical interoperability:** no physical passport, device NFC/RF or production app test was performed. Record v0/v1, legacy/new DG2, PACE/CA/AA, large reads, recovery, cancellation, timeouts and repeated scans across issuer/device/OS feature classes without collecting passport contents. All new evidence is synthetic, local cryptography, iOS Simulator and generic iOS compilation.
2. **Restricted-workflow project, explicitly deferred by the user:** TA v1/CVC chain verification and terminal signing credentials, authenticated access to protected DG3/DG4, and LDS2 travel/visa/additional-biometric applications. Design opt-in result/retention APIs and provision authorized credentials before implementation. Reading an opaque file ID does not grant this access. Do not add writes as part of reader support. TA v2 and proprietary encrypted-biometric schemes are outside ICAO's ordinary LDS1 profile.
3. **Trust-data operations:** authenticated master-list acquisition, CRL refresh/rollback protection across launches, root/CSCA revocation decisions and production PKD distribution belong to the consuming trust-store workflow. The reader checks supplied document-signer CRLs; it does not certify the bundle's provenance/freshness beyond signature and validity times or implement online OCSP. Test production CSCA rollover catalogs separately from the synthetic link-chain case.
4. **External conformance/fuzzing:** the new positive inventory prevents the implementation allowlist from defining its own acceptance universe, but optional face metadata, unusual issuer certificate paths, uncommon AA curves and full protocol/device combinations need broader independent corpora. Existing legacy CA inference when CAInfo is absent remains a compatibility heuristic; it does not establish that such metadata meets the current profile. Unknown optional SecurityInfo entries are ignored as ICAO permits; unsupported security mechanisms never report successful authentication.
5. **App integration:** publication is complete using the repository-owning account; remote main and both newly published annotated tags were verified. The app pin remains unchanged and should be updated to rc.7 in the app repository, followed by the physical integration checks above.

`.notaryStrict` still requires passive signature/read-group integrity. It does not require issuer trust, revocation, every advertised group, or an available photo. Apps needing these guarantees must select the corresponding trust/revocation policy and check the result's photo/coverage fields.

The second audit also reproduced the rc.6 PSS declaration and first-certificate trust defects against unchanged production code: 2 tests, 4 expected failed assertions. Current signed-profile tests reject both.

The SOD v1 defect should have been caught by positive standards acceptance: rc.5's regression deliberately expected the valid v1 parser failure. A green diagnostic regression was incorrectly usable as a compatibility signal. The replacement test and this independently enumerated inventory make that distinction explicit.
